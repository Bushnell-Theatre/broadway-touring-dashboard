# Developer Guide — Broadway Touring Intelligence Dashboard

This document covers the JavaScript architecture, the `BTD` shared namespace, how pages are structured, and how to extend the signal model or add shared helpers.

---

## Architecture Overview

The dashboard is a **fully static** application. There is no build step, no framework, no npm. Every file the browser loads is a plain `.html`, `.css`, or `.js` file served as-is from Azure Static Web Apps.

## The BTD Namespace

All shared JavaScript attaches to `window.BTD`. This avoids global name collisions and makes the dependency graph explicit.

```javascript
window.BTD = window.BTD || {};
BTD.config    // constants and thresholds
BTD.state     // current season, filters, loaded show/peer data
BTD.fmt       // formatters (fmt$, pct, num)
BTD.metrics   // per-show metric aggregation
BTD.data      // fetch wrappers and data loading
BTD.signals   // Planning Signal model (canonical)
BTD.charts    // Chart.js lifecycle helpers
BTD.components // card/table/rank rendering
BTD.page      // callout/headline/copy logic shared across pages
BTD.analytics // dashboard-only calculations
```

Each file opens with `window.BTD = window.BTD || {}` before adding its sub-namespace, so module load order within a page is flexible as long as all core files precede the page controller.

### Script load order in HTML

```html
<!-- 1. Third-party -->
<script src="https://cdn.jsdelivr.net/.../chart.umd.min.js"></script>

<!-- 2. Shared core (any order within this group) -->
<script src="js/utils.js"></script>
<script src="js/core/config.js"></script>
<script src="js/core/format.js"></script>
<!-- ... remaining core modules ... -->
<script src="js/core/page-common.js"></script>

<!-- 3. Page controller (always last) -->
<script src="js/pages/programming.page.js"></script>
```

## Planning Signal Model

The canonical model lives in `src/js/core/signals.js`. Pages call it via the shared
entry point in `page-common.js`:

```javascript
var profile = BTD.page.profileShowCanonical(show, allRows, options);
// Direct call (non-page code only):
var profile = BTD.signals.profileShow(show, records, options);
```

Returns (contract-compliant shape — see `docs/SCORING_CONTRACT.md`):

```javascript
{
  title,          // normalized show title string (top-level)
  show,           // original show object passed in; if show was a string,
                  //   { title: titleOf(show), match: matchOf(show) }
                  //   Do not assume a normalized { title, season, status } shape.
  metrics: {
    gross,        // avg weekly gross ($) — alias: grossGross
    gg,           // avg GG% of gross potential — alias: ggPctGp
    cap,          // avg paid capacity % — alias: paidCapacity
    peerCap,      // avg capacity across all peer types (deduplicated union)
    index,        // Bushnell index vs national cap (Hartford records only)
    count,        // number of weekly records matched — alias: recordCount
    weeks,        // number of reporting weeks — alias: weekCount
    venueCount    // distinct venues in the national matched pool
  },
  signals: {
    demand:     { value, label, drivers },  // value: 0–100 or null
    revenue:    { value, label, drivers },
    peer:       { value, label, drivers },  // value === 0 means zero peer records
    confidence: { value, label, drivers }
    // signals also includes recognition, press, tour, risk, audience, local
    // (each { value, label, drivers }) — used for supplementary display only
  },
  score,          // 0–100 composite integer or null (null = no evidence)
  planning: {
    read,         // "Strong Candidate" | "Mixed: Demand Ahead of Revenue" |
                  // "Upside: Revenue Ahead of Demand" | "Discuss" | "Watch" | "Exploratory"
    note          // one-sentence interpretation string (may be '')
  },
  decomp: {
    canonical,    // always true — marks this as the canonical scorer's output
    demand,       // rounded demand component value (same as p.signals.demand.value)
    revenue,      // rounded revenue component value
    peer,         // rounded peer component value
    confidence,   // rounded confidence component value
    peerTypes     // string describing which cohort types contributed, e.g.
                  //   "size (5 records), proximity (3 records)"
  },
  isFutureNewTour // true if no historical records exist yet
}
```

**Note:** The top-level `read` field was removed. Use `p.planning.read`. The flat
`signals.demand` (numeric) shape was replaced with `signals.demand.value` + `.label`
+ `.drivers`. Pages that call `BTD.page.planningSignals(profile)` receive only
label strings and do not need to access `p.signals` directly.

`decomp` values duplicate the rounded component signal values — they are not raw
pre-scale inputs. Use `p.signals.*.value` for the same data; `decomp` is retained
for debugging and logging.

### Signal thresholds

All numeric thresholds are defined in `src/js/core/config.js`. Change them there only — never in page controllers or `page-common.js`.

### GG% callout thresholds

| GG% | CSS class | Meaning |
|---|---|---|
| ≥ 80% | `.good` (green) | Strong revenue performance |
| 60–79% | (neutral) | Acceptable |
| < 60% | `.warn` (amber/red) | Substantially below gross potential |

These thresholds live in `BTD.page.seasonCalloutClass()` in `page-common.js`. Both Programming and Executive Summary call this same function — the season headline color is always driven by GG%, not capacity.

## Shared Page Helpers (`page-common.js`)

Three functions that both Programming and Executive Summary share. They live in `BTD.page` so thresholds and copy logic have a single source of truth.

### `BTD.page.seasonCalloutClass(avgGG)`

Returns the CSS class for the season callout banner based on GG%. Output: `'good'`, `''` (neutral), or `'warn'`.

### `BTD.page.seasonHeadline(avgGG, avgGross, peer, profiles)`

Returns the headline sentence. Reads actual profile data — names the top-grossing show by title, the real GG%, and the count of matched shows. This copy changes every week as new data is ingested.

Example:
> "Hamilton leads at $1.2M avg gross · season at 84% GG% across 8 matched shows."

### `BTD.page.seasonSummaryCopy(profiles, avgGG, avgGross, avgCap, peer)`

Returns a multi-sentence body paragraph. Names specific strong performers (GG% ≥ 80%) and soft signals (GG% < 60%) by show title. Ends with a capacity context footnote.

## Adding a Shared Helper

1. Decide which core module it belongs to (formatting → `format.js`, metrics → `metrics.js`, page copy → `page-common.js`).
2. Add the function at the module level.
3. Expose it on the `BTD.*` namespace at the bottom of the file, guarding the sub-namespace first.
4. Call it from page controllers with a fallback for graceful degradation.

```javascript
// In page-common.js:
function myHelper(value) {
  return value > 0 ? 'positive' : 'negative';
}
BTD.page = BTD.page || {};
BTD.page.myHelper = myHelper;

// In a page controller:
var result = (BTD.page && BTD.page.myHelper)
  ? BTD.page.myHelper(val)
  : 'fallback';
```

The defensive guard (`BTD.page && BTD.page.myHelper`) ensures the page degrades if a core file fails to load, rather than throwing a hard error.

## Page Controllers

Each page controller is a **classic non-module script**. It uses module-level `let`/`var` globals and `DOMContentLoaded`. It is intentionally not an ES module because inline HTML event handlers (e.g., `onclick="showTab('brief')"`) require globals.

### Typical structure

```javascript
// Module-level state
var ALL = [], SEASONS = [], PROFILES = [], SCORE_MED = 50;
var STATE = { season: null, filter: '' };

document.addEventListener('DOMContentLoaded', function() {
  loadData();
});

function loadData() {
  // Fetch data.json, shows.json, seasons.json, peers.json, context.json
  // shows.json fetch uses BTD.data.loadShows() which returns [] if file is absent
  // Then call renderAll()
}

function renderAll() {
  // PROFILES = BTD.signals.profileShow() for each slate show
  // SCORE_MED = median of profile scores
  // Call renderBrief(), renderActive(), renderHistory(), renderPlanning(), renderPeers()
}
```

### Rules for page controllers

- Do **not** put scoring or threshold logic in page controllers. It belongs in `signals.js` or `config.js`.
- Do **not** duplicate callout/headline/copy logic. Use `BTD.page.*` functions.
- Page-specific HTML structure and tab behavior belongs in the page controller — that's appropriate.

## Missing Data File Handling

Pages are designed to degrade gracefully when optional files are absent:

| File | If absent |
|---|---|
| `shows.json` | Intelligence tab shows an inline message; all other tabs work normally |
| `validation_report.json` | Dashboard validation panel shows no data; no error thrown |
| `context.json` | Context badges are omitted; show scores are unaffected |

`data.json`, `seasons.json`, and `peers.json` are required — pages will not render meaningful content without them.

## Charts

Charts use Chart.js 4.x loaded from CDN. The `BTD.charts` module provides lifecycle helpers:

```javascript
BTD.charts.renderDashboardChart(CHARTS, key, canvasId, config);
```

`CHARTS` is a registry object keyed by short string (`'sg'`, `'wk'`, etc.). Calling `renderDashboardChart` destroys any existing chart at that key before creating a new one, preventing canvas reuse errors on re-render.

See [CHARTS.md](CHARTS.md) for what each chart shows and what decisions it supports.

## CSS Design System

All colors, spacing, and typography are CSS custom properties in `src/css/styles.css`.

Key variables:

```css
--ink1       /* primary text */
--ink2       /* secondary text */
--ink3       /* metadata / tertiary */
--bg1        /* page background */
--bg2        /* card background */
--accent     /* Bushnell blue #003865 */
--good       /* green — strong performance */
--warn       /* amber/red — below threshold */
```

Status classes `.status.good`, `.status.warn`, `.status.neutral` are used on score badges and table cells throughout all pages.

Do not modify `styles.css` without explicit direction — visual identity changes have downstream effects across all pages and all chart colors.

## Do Not Break

These constraints are intentional:

1. Do not convert page controllers to ES modules without replacing all inline HTML event handlers.
2. Do not collapse Demand and Revenue into one score — they measure different things.
3. Do not treat Revenue Signal as net profit — it is gross revenue quality only (deal terms, local expenses, and ancillary revenue are not yet modeled).
4. Do not remove above-100 capacity/gross values — they are valid Broadway League reporting conditions.
5. Do not put scoring or threshold logic in page controllers — all thresholds belong in `config.js` and `signals.js`.
6. Do not add a frontend build step without explicit agreement — the no-build constraint keeps hosting free and deployments trivial.
